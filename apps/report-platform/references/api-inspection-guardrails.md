# API Inspection Guard Rails

Sources consulted:

- `API 653 5th Ed (Nov 2014), Add 1 (Apr 2018), Add 2 (May 2020).pdf`
- `API 575 4th Ed (Jul 2020).pdf`

This file is intentionally paraphrased. It is not a substitute for the standards.

## Use this file for

- section drafting guard rails
- section-scoped AI prompts
- reviewer reminders about what must not be invented

## Key paraphrased themes

### General reporting

- Inspection reporting should remain evidence-based.
- Assessment language should follow verified measurements, visual evidence, and confirmed assumptions.
- Recommendation wording should not outrun the supporting inspection basis.

### External and visual inspection

- External inspection should focus on conditions that may affect serviceability.
- Visual observations should be tied to actual observed conditions rather than generic boilerplate.

### Roof and shell reporting

- Roof and shell comments should align to recorded measurements and visible conditions.
- Layouts should support location understanding, not replace measurement evidence.

### Nozzles and attachments

- Nozzle-related comments should reflect actual inspected condition and measured data.
- Do not imply pad or reinforcement measurements if only registry or note data exists.

### Calculations and assessment

- Calculation-driven sections should rely on deterministic inputs and outputs.
- Do not generate minimum thickness or assessment results from narrative alone.

### Deferred floor and MFL sections

- If floor or MFL evidence is missing, the report should say so.
- Missing sections should be blocked or marked deferred rather than fabricated.
